App Overview

PROBLEM + SOLUTION

The Problem

  • ▸ LinkedIn's interface is cluttered and overwhelming for new professionals
  • ▸ Reaching out to connections is intimidating with no guidance on message quality
  • ▸ No feedback on whether a profile is "ready" to start networking
  • ▸ Cold-start problem: new users don't know where to begin

Our Solution — Nexus

  • ▸ Clean, modern SPA with familiar LinkedIn-like experience
  • ▸ AI Outreach assistant that drafts tailored connection messages
  • ▸ Profile readiness scoring (9-criterion weighted, 0–100) before reaching out
  • ▸ Full networking workflow: posts, connections, messaging, jobs

Target Users

🎓
Students & New Graduates
Building their first professional network; unsure how to start
💼
Early-Career Professionals
Actively job hunting, looking to make meaningful connections
🔍
Career Changers
Entering new industries and needing guided outreach help

Key Differentiator

Nexus is the only LinkedIn-style app with a built-in Outreach Readiness Score and an AI message drafting assistant. Users get actionable feedback before sending a single connection request.

Frontend Delivery

Secrets & Permissions

SECURITY MODEL

GitHub Secrets

Secret Used by Purpose
RENDER_BACKEND_DEPLOY_HOOK deploy-render-backend.yml Trigger Render redeploy via webhook URL

No AWS keys. No database credentials. Deploy hook is revocable from the Render dashboard at any time.

API Authentication

  • Login/register in index.html — plain JS, no React
  • Server returns a session token (stored in localStorage['nx-token'])
  • All API calls send Authorization: Bearer <token>
  • app.html auth guard redirects to index.html if no token
  • Backend _require_auth_user() aborts with 401 on invalid/missing token

Security Hardening (Added During P5)

  • SRI hashes on all CDN <script> tags — prevents CDN tampering
  • All mutation routes guarded by _require_auth_user()
  • Thread-safety lock on add_education / add_skill
  • escapeHtml() used everywhere user content is injected into DOM
  • JSON body guard: non-dict payloads silently return {}
  • Input validation: tone, goal, and custom note length all validated at API boundary

Permissions Model (GitHub Actions)

  • All test workflows use default read-only permissions
  • Deploy workflow only needs outbound HTTP (curl) — no repo write access
  • No third-party Actions with write permissions
  • Coverage artifact upload uses actions/upload-artifact@v4 (official)

How Failures Impact Deployment

  • Any test failure → workflow exits non-zero → GitHub marks check as failed
  • PRs to main cannot merge while checks are red (branch protection)
  • deploy-render-backend.yml only runs on push to main — broken code never reaches it
  • Coverage below 80% → CI fails before any deploy step is reached
  • Smoke test failure = live service issue — alerts team immediately via GitHub

What Integration Tests Cover

  • Auth: register, login, bad credentials, duplicate email
  • Feed: create, like, comment, delete, pagination
  • Profile: GET /me, PUT /me, experience, education, skills
  • Jobs: browse, filter by keyword/location, apply
  • Messaging: list conversations, send message, read thread
  • Outreach: readiness score, message generation, validation
  • Network: send/accept/withdraw connections

Postmortem — Failures & Surprises

WHAT BROKE · WHAT SURPRISED US
🔒

Security Gaps Discovered Late

Multiple routes lacked auth guards — found during P5 security review. _require_auth_user() had to be retroactively applied to ~15 routes. Should have been part of the initial route template.

🔘

Stub Actions Were Underestimated

A large number of UI buttons were initially "coming soon" stubs. Wiring every action to real backend logic took several full PRs and far more time than expected — it wasn't just "filling in" code.

❄️

Render Free-Tier Cold Starts

The smoke test CI job failed repeatedly because the 30-second cold start exceeded initial timeout limits. We had to extend the timeout to 3 minutes and add retry loops — a known Render free-tier limitation we didn't plan for.

📦

JSON Body Edge Cases in Flask

Non-dict JSON payloads (arrays, null) caused unhandled exceptions on several routes. Required a _get_body() guard helper to be added defensively everywhere — not a hard problem but caught us off guard.

🔄

PR Review Iteration Took Longer Than Expected

CodeRabbit and Copilot reviews generated 5–6 rounds of comments per PR. While this improved quality, we didn't budget time for it — some PRs took 2–3× as long as estimated to land.

🗄️

SQLite on Render Resets on Redeploy

Render's free tier does not persist disk between deploys by default. The database reseeds correctly from data/*.py, but user-created data (posts, accounts) is lost on each deploy — a limitation for long-term demo use.

LLM Usage Analysis

HOW AI SHAPED DEVELOPMENT

Primary Tools Used

  • Claude (Anthropic) — architecture decisions, full component generation, debugging, CI config, security review
  • GitHub Copilot — inline autocomplete, PR review comments
  • CodeRabbit — automated PR review, style enforcement

Where LLMs Were Most Effective

  • Generating boilerplate React components (14 pages, 12 modals)
  • Writing comprehensive pytest test suites (2,700+ line test file)
  • Configuring GitHub Actions workflows from scratch
  • Identifying security vulnerabilities (auth gaps, XSS risks)
  • Debugging tricky Flask/React integration issues

Challenges & Prompt Iteration

  • Complex components (MessagingPage, ProfilePage) needed 4–6 prompt rounds to get right
  • LLM-generated tests needed manual review — some tested the wrong behavior
  • CI/CD config required iteration to handle Render cold-start edge case
  • Needed to provide full file context to avoid hallucinated imports

How We Improved Confusing Outputs

When LLM output was incorrect: (1) provided the full file for context, (2) described the exact failure mode, (3) asked for explanation before code. This reduced wasted iterations significantly. For CI issues, attaching the raw workflow error log was the single most effective debugging prompt.

Net Assessment

LLMs were a force multiplier — not a replacement for engineering judgment. The team still had to understand every line generated, catch hallucinated APIs, and make architectural decisions. The biggest gain was in speed: tasks that would take hours (writing 100 test cases, setting up CI) took minutes with AI assistance.

Lessons Learned

WHAT WE'D DO DIFFERENTLY

🔐 Security Review Must Be Day 1

Auth guards, input validation, and XSS prevention should be designed into route templates from the start — retrofitting security after the fact is expensive and error-prone.

⏱️ Budget Time for PR Review Iterations

Automated code review (Copilot, CodeRabbit) generates real, actionable feedback. Each PR should have 2× the estimated time to account for review rounds — it's worth it, but it's not free.

🏗️ Define API Contract Before Building Frontend

Several frontend components had to be rewritten when the backend API shape changed. A simple OpenAPI schema agreed on in Week 1 would have prevented most of this churn.

🧪 Write Integration Tests Alongside Features

Integration tests written after the fact were harder to scope and missed edge cases. Writing them in the same PR as the feature would have caught issues earlier and made the code easier to reason about.

🗄️ Choose a Persistent DB for Production

SQLite on Render resets on redeploy. For a real app, we'd use PostgreSQL (Render offers a managed free tier). Switching from SQLite to Postgres is a one-day migration — we'd do it in week 2 next time.

🤖 Scope LLM Prompts to Single Responsibilities

Large, vague prompts ("build the messaging feature") produced large, incorrect outputs. Small, precise prompts ("add a DELETE /api/feed/:id route that checks ownership") were dramatically more reliable and faster to review.

Future Work

ROADMAP — NEXT 5 FEATURES
🧠

Real AI Integration (AWS Bedrock)

The _call_ai() function in outreach.py is already the designated swap point. Wiring in Bedrock (Claude or Titan) would make outreach drafts genuinely personalized — reading the recipient's profile to generate highly targeted messages.

⚡

Real-Time Messaging (WebSockets)

Current messaging uses polling. Replacing with Flask-SocketIO + a client-side WebSocket would give true real-time delivery. This is the single highest-impact UX improvement possible without changing the feature set.

🗄️

PostgreSQL Migration

SQLite resets on Render redeploy and doesn't support concurrent writes at scale. Migrating to Render's managed PostgreSQL (free tier available) would give persistent data and production-grade reliability with minimal code change thanks to the clean database.py abstraction layer.

📱

Progressive Web App (PWA)

Adding a service worker and web app manifest would allow Nexus to be "installed" on mobile devices, work offline for cached content, and send push notifications for connection requests — all without a native app.

📊

Analytics Dashboard + Connection Recommendations (ML)

Profile view counts, post engagement metrics, and a recommendation engine ("people similar to your network") using collaborative filtering on the connection graph. This would close the loop on the Outreach Readiness feature — showing users how their profile quality correlates with actual engagement.
